## Overview (introduction/overview)

gh-aw "lets developers define AI-powered repository automation in Markdown with YAML frontmatter and run AI agents through GitHub Actions." An agentic workflow can "understand context, make decisions, and take meaningful actions—all from natural-language instructions written in Markdown," in contrast to rigid if-then automation.

A workflow file has two parts: YAML frontmatter (triggers, permissions, allowed operations) and a Markdown body (natural-language instructions to the agent). Canonical example (verbatim):

```yaml
---
on:                        # Trigger: when to run
  issues:
    types: [opened]
permissions: read-all      # Security: read-only by default
safe-outputs:              # Allowed write operations
  add-comment:
---
# Issue Clarifier
Analyze the current issue and ask for additional details if the issue is unclear.
```

`gh aw compile` transforms the Markdown source into a hardened GitHub Actions workflow (`.lock.yml`); the compile step "validates the configuration, applies security hardening, and generates the workflow file that GitHub Actions can execute." By default agents run read-only; authorized writes go through sanitized safe-outputs.

## Architecture and security model (introduction/architecture)

Layered defense-in-depth with three trust boundaries. Threat model: adversaries may compromise user-level components and "behave arbitrarily within the privileges granted to them" — attempting memory access, unauthorized communication, channel abuse, workflow deviation. Explicitly out of scope: hardware compromise and cryptographic attacks.

**Layer 1 — Substrate-level trust**: GitHub-hosted or Linux self-hosted runners; Docker daemon (default) or privileged ARC DinD sidecars; optional gVisor (user-space kernel) or Docker sbx (KVM microVM) runtimes. Verbatim: "The trusted substrate therefore includes the runner host or Kubernetes cluster, CPU, MMU, kernel, and container runtime."

**Layer 2 — Configuration-level trust**: declarative specs (workflow YAML, network policies, MCP configs) define structure and connectivity; auth tokens "bound components' external effects."

**Layer 3 — Plan-level trust**: the compiler decomposes workflows into stages with explicit permissions, data flow, and output handling. SafeOutputs is the exemplar — agents never hold write permissions; all externalized writes flow through separate validated jobs.

Compilation pipeline (verbatim):

```
Workflow.md → Schema Validation → Expression Safety → Action SHA Pinning
  → Security Scanners → .lock.yml (validated output)
```

Compilation-time security: JSON schema validation of frontmatter; expression allowlisting (no secrets in expressions); action SHA resolution and caching (supply-chain pinning); integrated scanners `actionlint` (with shellcheck/pyflakes), `zizmor` (privilege escalation), `poutine` (supply-chain risks). Strict mode (default `strict: true`): no write permissions, explicit network config required, no wildcard domains, no deprecated fields.

Compiled job execution structure:

- **Pre-activation job**: role/permission checks, stop-after deadline enforcement, skip-if-match validation, command position checks.
- **Activation job**: workflow context preparation, event text sanitization, lock file validation.
- **Agent job (read-only)**: repo checkout, runtime setup (Node.js, Python), MCP container startup, AI engine execution, unconditional secret redaction (`if: always()`), artifact upload.
- **Detection job (isolated, no write permissions)**: downloads buffered artifacts, runs security-focused AI analysis, emits pass/fail verdict.
- **Safe-output jobs (scoped writes only)**: e.g. `create_issue` (issues:write), `add_comment` (issues:write), `create_pull_request` (contents:write + pull-requests:write), `add_labels` (issues:write). All safe-output jobs execute only after threat-detection approval.

Safe-outputs permission isolation (verbatim): "The agent never requires write permissions because all write operations are performed by separate, validated jobs with minimal scoped permissions." Agent output is buffered as artifacts (`agent_output.json`), downloaded by the detection job, analyzed for threats, and only then passed to write-enabled safe-output jobs.

**Agent Workflow Firewall (AWF)**: containerizes the agent and enforces network egress. Agent runs in an isolated Docker container; a Squid proxy enforces a domain allowlist via iptables; HTTP/HTTPS traffic is redirected through the proxy; setup drops iptables capabilities before agent launch. Two modes: default (full container isolation with host binary access via `/host` chroot) and chroot mode (host dirs read-only, HOME and /tmp read-write, controlled env-var subset). Runner/runtime combinations: GitHub-hosted or self-hosted + Docker (internal network + Squid proxy); ARC DinD (privileged sidecar creates isolated network); compatible Linux + gVisor (`runsc` user-space kernel interposition); KVM-capable + Docker sbx (hardware-virtualized microVM).

Network controls in frontmatter:

```yaml
network:
  firewall: true
  allowed:
    - defaults        # Certificates, JSON schema infrastructure
    - python          # PyPI, Conda ecosystems
    - node            # npm ecosystem
    - "api.example.com"  # Custom domain
```

Egress policy (verbatim): "All traffic routed through proxy enforcing the domain allowlist."

**MCP gateway and sandboxing**: MCP servers execute in isolated containers; the gateway spawns them via the Docker socket, routes agent requests through the Squid proxy, and enforces tool allowlisting at configuration level. Stated limitation (verbatim): "The MCP gateway agent ID is not a strong security boundary against a compromised or malicious agent."

**Content sanitization** (activation stage, for untrusted input): `@user` → `` `@user` `` (@mention neutralization, prevents notifications); `fixes #123` → backticked (bot-trigger protection, blocks auto-linking); `<script>` → `(script)` (XML/HTML conversion, XSS prevention); non-HTTPS and untrusted-domain URIs → `(redacted)` (allowed domains include github.com, api.github.com, and configured custom domains); content limits truncate at 0.5MB / 65k lines (DoS mitigation); ANSI escapes / control characters stripped.

**Integrity filtering**: controls which GitHub content agents access based on author trust and merge status, not just push access. Four cumulative levels, most to least restrictive: `merged` (merged PR content only), `approved` (owners/members/collaborators — auto-applied for public repos), `unapproved`, `none`. Verbatim: "Individual users can be blocked unconditionally, and trusted reviewers can promote specific items via approval labels."

**Secret redaction** (unconditional, `if: always()`): scans workflow YAML for `secrets.*` patterns, extracts names and values, finds files in `/tmp/gh-aw` (*.txt, *.json, *.log, *.md, *.yml), replaces exact matches with masked values (first 3 chars + asterisks). Verbatim: "This mechanism prevents accidental credential leakage through logs, outputs, or artifacts."

**Threat detection pipeline**: inputs are the buffered artifacts (`agent_output.json`, `aw.patch`, `prompt.txt`); a detection agent runs isolated from the original agent with a security-focused system prompt, analyzing for secret leaks, malicious patches, policy violations; supports custom detection prompts and steps:

```yaml
threat-detection:
  prompt: |
    Check for internal infrastructure URLs,
    CI/CD configuration modifications
  steps:
    - name: Run TruffleHog
      run: trufflehog filesystem /tmp/gh-aw --only-verified
```

Verdict must pass before safe-output jobs execute.

**Observability artifacts** preserved per run: `agent_output.json` (AI decisions/actions), `prompt.txt` (generated prompts), `aw.patch` (code changes), engine logs (token usage, timing), firewall logs (network requests). CLI: `gh aw logs` (download and analyze runs), `gh aw audit` (investigate failures), `gh aw status` (workflow health).

## Engines (reference/engines)

Five built-in engines, selected via the `engine:` frontmatter field:

| Engine | id | Authentication | Status |
|---|---|---|---|
| GitHub Copilot CLI | `copilot` | `copilot-requests: write` permission or `COPILOT_GITHUB_TOKEN` | Default (production) |
| Claude Code | `claude` | `ANTHROPIC_API_KEY` or Anthropic WIF | Production |
| OpenAI Codex | `codex` | `CODEX_API_KEY` or `OPENAI_API_KEY` | Production |
| Google Gemini CLI | `gemini` | `GEMINI_API_KEY` or Google WIF | Production |
| Pi | `pi` | Copilot auth by default; Anthropic/OpenAI keys for provider-prefixed models | Production |

- Verbatim: "Copilot CLI is the default, so `engine:` can be omitted when using Copilot."
- Each engine's native CLI tool is installed automatically on the runner and invoked in the agent job.
- Custom engines: nested object form with `engine.id` referencing an imported workflow definition — "There is no flat `engine: custom` value"; only built-in ids or imported identifiers are valid.
- Unsupported engine samples exist in the repo (OpenCode, Aider, Crush, Cursor, DeepSeek Harness, Kiro, Pydantic AI) but "are **samples only**. They are not officially supported by gh-aw."
- Engine field extras: `engine.driver` (runtime override, `node:`/`python:` inline source), `engine.extensions` (engine-specific plugins, e.g. `["@pi/web-search"]`, Pi only), `engine.concurrency` (see concurrency section).

## Triggers (reference/triggers)

Standard GitHub Actions triggers with agentic enhancements.

Event-based: `issues` (`types: [opened, edited, labeled]`), `pull_request` (`types: [opened, synchronize, labeled]`), `issue_comment` (`types: [created]`), `repository_dispatch` (`types: [jira-issue-created]` — external system integration), `workflow_run` (chain on completion of named workflows, filter by `conclusion: [failure, cancelled]`), `deployment_status` (`state: [error, failure]`), `pull_request_target` (base-repo context; supports `forks: ["trusted-org/*"]` and `max-stack: 1` for stacked-PR chains).

Schedules: cron (`- cron: "30 6 * * 1"`) plus fuzzy natural-language schedules that scatter execution — `daily around 14:00`, `daily between 9:00 and 17:00`, `weekly on monday`. Manual: `workflow_dispatch` with typed `inputs:`.

Command triggers:

```yaml
on:
  slash_command:
    name: investigate
    events: [issues, issue_comment]
```

and `label_command: deploy` (activates on label application and auto-removes the label).

Role-based access control on triggers — `roles:` defaults to admin/maintainer/write; verbatim: "Roles is an **exact-match allowlist**, not a privilege threshold" (setting only `write` rejects admins). Available roles: `admin`, `maintainer`, `write`, `triage`, `read`, `all`. Also `bots:` allowlist (e.g. `["dependabot[bot]", "renovate[bot]"]`), `skip-author-associations:`, label `names:` filters, and search-query gates `skip-if-match:` / `skip-if-no-match:` (GitHub search syntax, optional `min:` count).

Cost/lifecycle controls on the trigger block: `cooldown: 4h` (no re-run until elapsed), `stop-after: "+7d"` (auto-disable triggering at deadline), `lock-for-agent: true` (lock the issue while the agent works), `manual-approval: production` (environment-based approval gate), `status-comment: true` and `reaction: "eyes"` (feedback comments/reactions), pre-activation `steps:` (custom filtering logic before the agent runs, consumed via `needs.pre_activation.outputs.*`). Per-trigger auth: `github-token:`, `github-app:` (client-id/private-key), scoped `permissions:`.

Shorthand syntax compiles to full YAML: `on: push to main`, `on: pull_request merged`, `on: issue opened labeled bug`, `on: manual`, `on: comment created`.

## Frontmatter field reference (reference/frontmatter)

Exact field names (all optional unless noted): `description:`, `intent:` (durable outcome), `emoji:`, `labels:`, `metadata:`, `on:`, `if:`, `imports:` (shared components, e.g. `- shared/common-tools.md`), `import-schema:` (typed inputs), `pre-steps:` / `steps:` / `pre-agent-steps:` / `post-steps:` (deterministic Actions steps around the agent), `jobs:` (custom Actions jobs), `cache:`, `checkout:`, `ambient-folders:` (e.g. `[.squad, .github/agents]`), `permissions:` (GitHub API scopes), `github-app:`, `engine:` (`copilot` | `claude` | `codex` | `gemini` | `pi`), `engine.driver:`, `engine.extensions:`, `network:` (`allowed: [defaults, python, api.example.com]`), `tools:`, `skills:` (e.g. `["mattpocock/skills/tdd@main"]`), `plugins:` (experimental), `mcp-scripts:` (inline custom MCP tools via JS/shell), `safe-outputs:`, `threat-detection-suppress:` (`{rule: CTR-012, reason: "...", expires: "2026-12-31"}`), `run-name:`, `runs-on:`, `runs-on-slim:` (framework jobs, `ubuntu-slim`), `timeout-minutes:`, `concurrency:`, `env:`, `excluded-env:`, `max-turns:` (default 500), `max-turn-cache-misses:` (default 5), `max-ai-credits:` (per-run AI-credit budget, default 1000, `-1` disables), `max-daily-ai-credits:` (24-hour budget), `user-rate-limit:` (`{max-runs-per-window: 5, window: 60}`), `secrets:`, `environment:` (deployment protection rules), `container:`, `services:`, `observability:` (OpenTelemetry OTLP export), `resources:`, `runtimes:`, `run-install-scripts:` (default false), `source:` (workflow origin tracking, e.g. `"githubnext/agentics/workflows/ci-doctor.md@v1.0.0"`), `redirect:`, `tracker-id:`, `private:` (prevent cross-repo installation), `check-for-updates:` (default true), `features:` (experimental toggles), `strict:` (enhanced security validation, default true).

## Tools and MCP (reference/tools)

The `tools:` field declares agent capabilities:

- `edit:` — file modifications in the Actions workspace.
- `github:` — GitHub API operations via the GitHub MCP server; read-only by default; `toolsets: [repos, issues]` selects toolsets; `min-integrity` ties into integrity filtering.
- `bash:` — shell execution with safe defaults (`echo`, `printf`, `ls`, `pwd`, `cat`, `head`, `tail`, `grep`, `wc`, `sort`, `uniq`, `date`, `yq`); `bash: []` disables all; `bash: ["echo", "ls", "git status"]` allowlists; `bash: [":*"]` unrestricted (caution); wildcards like `git:*` for command families.
- `web-fetch:` / `web-search:` — "Some engines require third-party Model Context Protocol (MCP) servers for web search."
- `playwright:` — browser automation (optional pinned `version:`).
- `cache-memory:` / `repo-memory:` — persistent cross-run memory (below).
- `timeout: 120` / `startup-timeout: 60` — per-operation and MCP-startup timeouts (seconds).

Custom MCP servers via top-level `mcp-servers:` (verbatim example):

```yaml
mcp-servers:
  slack:
    command: "npx"
    args: ["-y", "@slack/mcp-server"]
    env:
      SLACK_BOT_TOKEN: "${{ secrets.SLACK_BOT_TOKEN }}"
    allowed: ["send_message", "get_channel_history"]
```

Options: process-based (`command`/`args`), Docker (`container`), HTTP (`url`/`headers`), `env`, tool restriction (`allowed`), startup criticality (`required`). MCP servers run in isolated containers behind the MCP gateway (see architecture).

## Safe outputs (reference/safe-outputs)

Mechanism: the agent runs read-only and emits structured requests; separate permission-controlled jobs execute them. Stated benefits: least privilege, defense against prompt injection, auditability, controlled operation limits.

Built-in safe-output types (exact names):

- Issues & discussions: `create-issue`, `update-issue`, `close-issue`, `link-sub-issue`, `create-discussion`, `update-discussion`, `close-discussion`.
- Pull requests: `create-pull-request`, `update-pull-request`, `close-pull-request`, `create-pull-request-review-comment`, `reply-to-pull-request-review-comment`, `submit-pull-request-review`, `resolve-pull-request-review-thread`, `add-reviewer`, `push-to-pull-request-branch`.
- Labels/assignment/comments: `add-labels`, `remove-labels`, `assign-milestone`, `assign-to-agent`, `assign-to-user`, `unassign-from-user`, `set-issue-type`, `set-issue-field`, `add-comment`, `hide-comment`.
- Projects/releases/assets: `create-project`, `update-project`, `create-project-status-update`, `update-release`, `upload-artifact`, `upload-asset`.
- Security & automation: `dispatch-workflow`, `call-workflow`, `dispatch-repository`, `create-code-scanning-alert`, `autofix-code-scanning-alert`, `create-check-run`, `create-agent-session`.
- System types (auto-enabled): `noop`, `missing-tool`, `missing-data`.

Common config: `max` (operation limit per run), `target` (`"triggering"` default, `"*"` any, or explicit number), `target-repo` (cross-repository operations, `"owner/repo"`), `allowed-repos`, `github-token`, `required-labels`, `required-title-prefix`. Issue-specific: `title-prefix`, `labels`, `expires` (auto-close, `7` days / `2w` / `1m`), `group` (sub-issues under a parent), `close-older-issues`, `deduplicate-by-title`. PR-specific: `protected-files` (e.g. `fallback-to-issue`), `reviewers`, `assignees`.

Example (verbatim):

```yaml
safe-outputs:
  create-issue:
    title-prefix: "[ai] "
    labels: [automation, agentic]
    max: 5
    expires: 7
    group: true
    close-older-issues: true
  add-comment:
    max: 3
    target: "*"
    hide-older-comments: true
  add-labels:
    allowed: [bug, team-*, area/*]
    blocked: ["~*", "*[bot]"]
    max: 3
```

All workflow-created items carry a hidden marker `<!-- gh-aw-workflow-id: WORKFLOW_NAME -->` for cross-repo discovery via GitHub search. Default behavior when no `safe-outputs:` section is given: `create-issue` auto-activates with conservative defaults (single issue per run, labels/title-prefix set to workflow id).

## Concurrency (reference/concurrency)

Dual-level concurrency. Workflow level, auto-generated groups by trigger type: issues → `gh-aw-${{ github.workflow }}-${{ issue.number }}`; PRs → `gh-aw-${{ github.workflow }}-${{ pr.number || ref }}` (cancels outdated runs); push → `gh-aw-${{ github.workflow }}-${{ github.ref }}`; scheduled/other → `gh-aw-${{ github.workflow }}`.

Engine level: a separate global group `gh-aw-{engine-id}` ensures "only one agent job runs per engine across all workflows, preventing AI resource exhaustion" — global because it excludes workflow name and context ids.

Both levels overridable in frontmatter (`concurrency:` and `engine.concurrency:`). Generated groups emit `queue: max` by default so "back-to-back triggers run sequentially rather than being dropped" (disable via `features.group-concurrency-queue: false`). `concurrency.job-discriminator` supports fan-out patterns without cross-cancellation.

## Cache memory and repo memory (reference/cache-memory)

`tools: { cache-memory: true }` gives persistent file storage across runs backed by the GitHub Actions cache, mounted at `/tmp/gh-aw/cache-memory/` (or `/tmp/gh-aw/cache-memory-{id}/` for additional caches). Advanced config: `key:` (compiler appends `${{ github.run_id }}` automatically — do not include it), `retention-days:` (1–90, artifact retention only), `allowed-extensions:`, and a `validation:` script with `timeout-minutes`.

Storage properties: Actions-cache backend; unused caches evicted after 7 days; 10GB per repository with LRU eviction; branch-local scope (restores from same branch, fallback to default branch). Default permitted file types: `.json`, `.jsonl`, `.txt`, `.md`, `.csv`; restored files are sanitized before agent execution (execute bits stripped, disallowed types removed). Multiple cache instances via a list with `id:` per entry.

Cache memory vs repo memory (docs comparison): cache-memory = Actions cache, ~7-day retention, 10GB/repo, no version control, best for temporary/session state; **repo-memory** = git branches, unlimited retention, repository size limits, version-controlled, best for long-term/history. (A private-preview "GitHub Drives" memory backend also appears in the llms.txt prompt index as `drive-memory`.)

Integrity-aware caching: with `tools.github.min-integrity`, cache keys include the integrity level and policy hash; data isolation is hierarchical (`merged` runs see only `merged` data; `unapproved` sees `unapproved`+`approved`+`merged`; etc.); changing an integrity policy forces a cache miss. Security note (verbatim): "Do not store sensitive data in cache memory. It follows repository permissions"; with threat detection enabled, caches persist only after validation succeeds. An agentic maintenance workflow auto-cleans outdated entries.

## CLI surface (setup/cli)

Setup: `gh aw init` (repo infrastructure: `.gitattributes`, dispatcher skills, Copilot agents/MCP config), `gh aw add-wizard`, `gh aw add` (install workflows from local files, remote repos, or URLs), `gh aw new`.

Build/validation: `gh aw compile` ("Compile Markdown workflows to GitHub Actions YAML. Remote imports cached in `.github/aw/imports/`" — supports linting, zizmor scanning, dependency analysis), `gh aw validate` (compile with all linters, no lock file emission), `gh aw fix` (codemods for deprecated fields).

Execution/testing: `gh aw run` (execute immediately in Actions), `gh aw trial` (test in temporary private repos, results saved to `trials/`).

Monitoring/analysis: `gh aw list`, `gh aw status` (enabled/disabled state, latest runs), `gh aw logs` ("Download and analyze logs with tool usage, network patterns, errors, warnings. Results cached for 10-100x speedup."), `gh aw audit` (single-run multi-section reports: prompt size, session performance, MCP server health, safe-output summaries; multi-run diff mode), `gh aw health` (success rates, duration, token usage, costs, trend indicators over 7/30/90-day windows), `gh aw forecast` ("Forecast AI Credit (AIC) usage for agentic workflows using recent run history and statistical simulation"), `gh aw outcomes` (safe-output disposition: accepted/rejected/ignored/pending; scoring against objective mappings), `gh aw models` (model catalog pricing, aliases, observed models).

Management: `gh aw enable` / `disable`, `gh aw remove`, `gh aw update` (3-way merge preserving local changes, driven by the `source:` field), `gh aw deploy` (roll out to target repos via PRs, org-wide), `gh aw upgrade`. Advanced: `gh aw mcp` (list/inspect/add MCP servers, tool discovery, secret validation), `gh aw mcp-server` (expose gh-aw commands as MCP tools over stdio or HTTP+SSE), `gh aw secrets`, `gh aw doctor`, `gh aw domains` (network domains configured across workflows), `gh aw hash-frontmatter`. GHES supported via `GH_HOST`; `--json` on commands for CI integration.
